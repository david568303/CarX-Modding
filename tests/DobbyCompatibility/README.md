# Dobby baseline/candidate compatibility

This source-only suite builds its own native fixture DLL and test hosts using
existing Visual Studio x64 tools and a .NET SDK. All hooks target fixture
functions in disposable child processes. No game files, game launch, OS API
hooks or remote process access are involved. It loads the actual BepInEx
assemblies from an **isolated extracted loader runtime**, never a game folder.

Use PowerShell 7, existing Visual Studio C++ x64 tools, an existing .NET SDK
capable of building net6.0, and a loader runtime containing its Python/Capstone
and CoreCLR 6.0.7 dependencies. The suite installs or downloads no compiler or
system runtime. Normal .NET project restore may use the configured package feed.

```powershell
pwsh -File .\tests\DobbyCompatibility\run-suite.ps1 `
  -Baseline 'C:\audit-inputs\original\dobby.dll' `
  -Candidate 'C:\audit-inputs\rebuilt\dobby.dll' `
  -RuntimeRoot 'C:\audit-inputs\extracted-loader-runtime' `
  -BuildRoot 'C:\audit-output\dobby-comparison-new'
```

All four parameters are required. `BuildRoot` must not exist and must be outside
`RuntimeRoot`. Optional `-DotnetExecutable` selects an existing `dotnet.exe`;
optional `-PythonExecutable` selects an existing Python with Capstone available.
By default it uses the runtime's own Python and the installed dotnet host. It
copies that existing host/hostfxr and the input runtime into a private layout,
and the managed test rejects anything except CoreCLR **6.0.7**. Runtime input
files are hashed before and after; baseline/candidate DLL hashes are recorded.
All generated objects, binaries, config and
results stay under `BuildRoot`.

The native host checks all seven exports and ordinals, deferred Prepare followed
by Commit/Destroy, original-trampoline behavior before activation, combined Hook,
RIP-relative load/LEA and relative-call relocation, conditional branches, six
integer arguments including stack arguments, floating arguments/returns,
nonvolatile integer registers, near-branch controls, repeated cycles and stable
parallel calls. Each library/case has its own child process.

The managed host loads the actual shipped `BepInEx.Unity.IL2CPP.dll`. It exercises
its `INativeDetour.Create` and `CacheDetourWrapper` with direct exports, E9 and
FF25 export thunks and a four-pointer callback signature. It checks trampoline
generation before Apply, callback/original delegate retention across collections,
stable parallel callbacks, Dispose restoring code/behavior and repeated Dispose.
It reports the existing `IsApplied` state after Dispose without changing the
production wrapper.

## Known baseline failure remains a failure

With original Dobby 1.0.5 SHA-256
`8015de7d867245a1095d13947a63763878e4cf5fd3d3089b63cc39200b055ded`
and the reviewed Windows source build
`fac2aa3399e8b73352181bfaa5fb9e3f55eb4ebf638d35c04a0857e5bc764001`,
the expected observations are **11 of 13 native cases passing on each DLL, two
matching native correctness failures, and four of four managed cases passing
on each DLL**.

Both native failures expose an existing x64 relocator bug in pinned Dobby source
`888d971214900374edbca6206fad6ded8a2c1311`, file
`source/InstructionRelocation/x64/X64InstructionRelocation.cc`: a two-byte Jcc
rel8 is widened to six bytes without subtracting the four-byte length change.
The generated branch lands four bytes past its intended target. The original
fixture runs correctly; its original trampoline already fails before Commit.
Both short and long function bodies are retained as regression fixtures.
The source-build candidate does not change Dobby's runtime implementation.

`probe-jcc.py` records original/generated bytes and decoded branch targets for
both DLLs. `comparison.json` distinguishes correctness failures from new
regressions. Address-dependent raw bytes can differ with ASLR; relative branch
target errors are recorded independently. The reviewed local run also produced
identical generated trampoline bytes for the original and source-built DLLs.

The suite deliberately exits **1** when these baseline correctness failures are
present, even when `noRegressionDetectedInExercisedCases` is true. Failures are
not skipped or converted into passes. Inspect `native-results`, `managed-results`,
`jcc-baseline.json`, `jcc-candidate.json`, `toolchain.json` and `comparison.json`.
No-regression results establish only the exercised compatibility; they do not
prove universal instruction-relocator or game/plugin correctness.
